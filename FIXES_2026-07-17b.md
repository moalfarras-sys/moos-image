# 2026-07-17 session H — the first-boot session: the zram storm, and a live session that locked its own installer

The owner's directive: walk the new ISO, fix EVERYTHING found, from the root,
in the source, with gates — then ship a clean ISO. The QEMU walkthrough of
`44.20260717.190` passed every existing check and found two shipped bugs no
gate had ever seen. Both are fixed on `main`; both gates were broken once on
purpose and watched go red.

## 1. A fresh install's first boot ended with failed units and NO swap

**Symptom** (installed target, first boot, QEMU): `moos-selfcheck` 38/39 —
`systemd-zram-setup@zram0.service` and `dev-zram0.swap` failed, `swapon --show`
empty. Second boot: clean. The owner's machine: never affected.

**The chain, from the extracted first-boot journal** (guestfish on the target
disk; the "phantom" `dev-disk-by\x2duuid-ec12418b….swap` in the errors is just
zram0's own by-uuid follower unit from its FIRST mkswap):

1. 08:38:40 — zram-generator sets zram0 up normally; swap active.
2. 08:38:48 — `moos-hardware-adapt` (stamped-idempotent, so it runs exactly
   ONCE — on first boot, the worst possible moment) rewrites
   `zram-generator.conf` for the RAM tier and calls
   `systemctl restart systemd-zram-setup@zram0.service`.
3. The restart stops the just-started `dev-zram0.swap` and re-starts it inside
   systemd's default start-rate window → `start-limit-hit`.
4. Every later setup retry dies with EBUSY writing
   `/sys/block/zram0/comp_algorithm` — the device is already sized — so one
   transient trip becomes a permanent-looking failure. Swap stays OFF.

**Fix** (`system_files/usr/libexec/moos-hardware-adapt`):
- Content-equality skip: if the config it would write is already on disk,
  it logs and leaves the running swap alone.
- The one legitimate apply is storm-proof:
  `stop dev-zram0.swap systemd-zram-setup@zram0` → `daemon-reload` →
  `reset-failed` (clears the start-limit counters) → ONE
  `start dev-zram0.swap` (pulls setup via Requires=) — then it says out loud
  whether the swap came back.

**Gate** (`tests/verify_user_experience.py`): on the comment-stripped script —
no `systemctl restart systemd-zram-setup@…` anywhere; the equality-skip must
exist; the four apply steps must appear in exactly that order. Broken once
(restored the bare restart): both requires went red.

## 2. The live session locked the screen over its own running installer

**Symptom**: during the walkthrough the install sat at "Copying MoOS — 86%"
behind the lock screen — KDE's stock 5-minute autolock is alive in the live
session, guarding a liveuser that HAS NO PASSWORD. On a real PC this reads as
a hang mid-install.

**Fix**: `moos-live-polish` (+ unit), enabled in `build.sh`:
- `ConditionKernelCommandLine=rd.live.image` — live boots ONLY (cmdline
  verified in the running live VM). An installed MoOS keeps its lock screen.
- `After=livesys.service` (livesys creates liveuser),
  `Before=display-manager.service` (the autologin session reads the config
  once, at start).
- Writes the LIVE USER's own `kscreenlockerrc` (Autolock=false,
  LockOnResume=false) and `powerdevilrc` (no dim, no display-off, no
  auto-suspend) — never `/etc/xdg`.
- Functionally tested in a container: files written and owned by liveuser;
  clean no-op when the user is absent.

**Gate**: unit must carry the rd.live.image condition (on EFFECTIVE lines only
— the first broken-once run proved a commented-out `Condition=` passed a raw
substring check, so the gate now strips comments before matching), the
ordering pair, the Autolock/LockOnResume keys, no `/etc/xdg`, a `getent`
no-op path, and the `systemctl enable` in build.sh.

## Traps worth remembering

- `git checkout <file>` after a break-the-gate test also reverts the UNCOMMITTED
  fix in that file. Re-apply and re-verify — the diff, not memory, is the truth.
- A unit-file gate that greps raw text is satisfied by a commented-out line.
  Strip comments first; break it once with `#Condition…` to prove the point.
- The first mkswap UUID shows up in errors as a `dev-disk-by\x2duuid-….swap`
  follower unit — it looks like a phantom fstab entry and is nothing of the
  sort. Check `systemd-makefs` lines before hunting ghost generators.
- Offline forensics beat screen-typing: power the VM down, `guestfish --ro`
  (LIBGUESTFS_BACKEND=direct) the journal out, and read it with
  `journalctl --directory` on the host.
