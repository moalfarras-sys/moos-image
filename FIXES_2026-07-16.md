# MoOS fixes — 2026-07-16 · remote input + terminal legibility

Driven by the owner's report after a reboot: Mo PC Remote controls the PC, but touch is
laggy, **Arabic typed from the phone does not appear**, and the **terminal text/colours
are hard to read**. Diagnosed on the running machine, fixed at the source (parity).

See the enduring principles in agent memory: one-system, source↔device parity, ISO hold,
Mo PC Remote is Tailscale-only.

---

## Shipped (source repo — pending `bootc upgrade` on the device)

### Correctness / blockers

- **Arabic (and any non-ASCII) typing from the phone now works** —
  `moremote/agent-linux/InputInjector.cs`, `TypeText`. The agent injected text as
  X11 Unicode keysyms (`0x0100_0000 + codepoint`) through the KDE RemoteDesktop portal's
  `NotifyKeyboardKeysym`. KWin can only emit a keysym that exists in the **active** xkb
  keymap; on the `us,ara` layout the Arabic keys map to the *legacy* Arabic keysyms
  (`0x05xx`), never the Unicode ones — so every Arabic character matched nothing and
  vanished. Worse, the D-Bus call itself *succeeds*, so the old code treated it as done
  and never fell back. Fix: `IsKeysymSafe()` — only printable ASCII goes down the keysym
  path (works on any layout); anything else (Arabic, accented Latin, box-drawing, control
  chars) routes through the existing layout-independent `wl-copy` + Ctrl-V paste path,
  which the ydotool fallback already used for the same reason.

- **Terminal bold text was invisible** —
  `artwork/generate_moos_ui2.py` (`konsole_scheme`) + regenerated
  `system_files/usr/share/konsole/MoOSUI2{Dark,Light}.colorscheme`. `ForegroundIntense`
  and `Color7Intense` (the colours Konsole uses for **bold** text, because the profile
  sets `BoldIntense=true`) were assigned `p["selected_text"]` — the ink meant for text
  drawn *on* an accent/selection highlight. That ink is dark in the dark theme and light
  in the light theme, i.e. the same side as the terminal background, so bold text (shell
  prompts, `ls`, `git`, headings) rendered near-invisible: dark-on-dark / light-on-light.
  This was the "الكلام مو واضح / الألوان مو واضحة" report. Fix: bold foreground/white now
  uses `p["text"]` / `base7` — always the foreground side, always legible.

### Robustness (related)

- **Generic `monospace` no longer resolves to an Arabic face** —
  `system_files/etc/fonts/conf.d/61-moos-brand.conf`. The JetBrains-Mono→Kawkab-Mono
  `accept` rule used `binding="strong"`, which promoted Kawkab Mono above the weakly-bound
  `monospace` preference of JetBrains Mono, so `fc-match monospace` returned **Kawkab
  Mono** and any app asking for the generic `monospace` alias drew Latin text in an Arabic
  face. Changed to `binding="weak"`: Kawkab stays a glyph-level fallback for the Arabic
  characters JetBrains Mono lacks, without ever winning the family sort. Konsole (which
  asks for JetBrains Mono by name) was already correct; this fixes editors/GTK apps that
  use the generic alias.

## Applied live for immediate relief (no image change)

- Corrected colour schemes copied to `~/.local/share/konsole/MoOSUI2{Dark,Light}.colorscheme`
  so bold text is legible **now**, before the upgrade. These are byte-identical to the
  regenerated image files; once the device runs the new image they are redundant and can
  be removed (`rm ~/.local/share/konsole/MoOSUI2*.colorscheme`). A new Konsole window (or
  tab) picks them up.

## Not an image bug — network

- **Laggy / "very slow" remote control** — `tailscale ping` reports *"direct connection
  not established"*: phone↔PC traffic relays through a DERP server (Frankfurt/Nuremberg)
  at 78–155 ms instead of a direct P2P hop. The firewall already opens UDP 41641, so this
  is the phone's network (cellular/CGNAT) defeating hole-punching, not the image. Putting
  the phone on the **same Wi-Fi as the PC** lets Tailscale connect directly over the LAN
  (still inside the tailnet — does not touch the `AllowLan=false` policy).
