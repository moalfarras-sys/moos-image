# 2026-07-17 session I — Mo AI's brains: the download the picker promised and never did

The owner asked, before any ISO: make the assistant's brains real. A user who
installs MoOS must be able to CHOOSE a brain, DOWNLOAD it from the internet, and
have it work with the app — three options, each good in Arabic, each able to talk
about repair/code/maintenance, none of them crushing the RAM and CPU. And the
cloud side must offer more than one API agent.

## What was actually broken (found by reading the live system, not the code alone)

### 1. "one-tap download" was a label with no machine behind it

The picker has printed **"تحميل بضغطة | one-tap download"** under every un-pulled
starter since the catalog shipped this morning. The tap called `pickRoute()` —
which only sets a route. The first chat then went to moai-gateway, which answers
a missing model with:

    النموذج «qwen3:8b» غير محمّل على هذا الجهاز.
    The local model "qwen3:8b" is not downloaded. Pull it first:
        ramalama pull qwen3:8b

A **terminal instruction**, on the one desktop whose whole promise is that you
never need the terminal. The catalog shipped; its download did not. The label was
true about the intent and false about the machine.

The gateway's refusal is RIGHT and stays: a chat message must never start a
multi-gigabyte download. What was missing is the explicit, watched act — so it
lives on the control API the picker already speaks:

- `POST /pull {"model": "<id>"}` — starts it. **Allowlisted to RECOMMENDED_LOCAL**:
  an arbitrary model string from the UI would be an arbitrary registry fetch, so
  `start_pull` refuses anything not in the catalog (proven: `evil; rm -rf /` and
  a real-but-uncurated `llama3.2:3b` both rejected).
- `GET /pull` — the state the picker polls: `{model, state, percent, error}`.
- Progress is **measured from RamaLama's store**, not parsed from `ramalama pull`
  output: with stdout on a pipe rather than a TTY that output carries no
  percentage at all (verified — the captured log says "Downloading qwen3" and
  stops). Blobs are shared per model FAMILY, so a per-model size is not
  attributable; the whole-store delta during a serialised pull is, and it costs
  ~1 ms on Btrfs. The bar never shows 100% while the process still runs — the
  last bytes are verification, and a full bar over a working process reads as a
  hang.
- Mo AI's row now taps `pickOrPull()`: pulled → switch; not pulled → download,
  draw the bar **on that row only**, keep the picker open (closing it over a
  running download is how a user concludes nothing happened and taps a second
  brain), then switch when it lands. A failure is said under the list instead of
  being swallowed.

### 2. A bare model tag resolves somewhere else entirely

MEASURED, and this one is a trap with no way out from the UI:

    ramalama pull qwen3:8b            → hf://Qwen/Qwen3-8B-GGUF
    ramalama pull ollama://qwen3:8b   → ollama://library/qwen3:8b

`short_model()` renders the first "Qwen/Qwen3-8B-GGUF", which matches **no id** in
the catalog — so the gateway reports a fully downloaded brain as missing, forever.
The pull now always prefixes `ollama://` (the same transport
`DEFAULT_LOCAL_MODEL` already names), and a gate holds it there.

### 3. The catalog was picked from claims, not from evidence

Every entry was re-MEASURED on this hardware, through the real gateway, in
Arabic, on a real repair question:

| brain | size | Arabic | verdict |
|---|---|---|---|
| `qwen3:1.7b` | 1.4 GB | three real commands; drops the "explain each" half | **kept** — the weak-machine tier |
| `qwen3:4b-instruct` | 2.5 GB | clean; drives moai-do | **kept** — stays the default |
| `qwen3:8b` | 4.9 GB | best of everything tried: right commands AND right explanations | **added** |
| `qwen2.5-coder:7b` | 4.4 GB | **broken**: emitted "الملفات الممكدة" (not a phrase) and invented an `lsof -m` flag | **rejected** — its code is excellent and its Arabic is not; MoOS is bilingual |
| `gemma3:4b` | 3.3 GB | never tested by anyone | **removed** — shipped this morning on an untested "broadest knowledge and languages" claim |

The rejections are recorded in the source next to the catalog so nobody re-adds
them on a hunch. "Ran here and survived" is the bar — the same rule that caught
the COSMIC camera and kamoso.

## Gates (each broken once on purpose and watched go red)

- `/pull` must exist in moai-control and `start_pull` must consult
  `RECOMMENDED_LOCAL` and reject unknown ids.
- The pull must carry the `ollama://` prefix (break: dropped it → red).
- The picker's tap must go through `pickOrPull`, and the old
  `onClicked: root.pickRoute(locRow…)` dead end must not come back (break:
  restored it → red).

## Verified on this machine

- Endpoint: injection string rejected, uncurated tag rejected, allowed starter
  downloaded to completion with progress.
- `qwen3:1.7b` removed from the store → `/models` reported `pulled: false` (after
  its 60 s cache) → the app was launched and the QML's own `pickOrPull` drove the
  download to 100% and switched to it, with no click (synthetic input does not
  reach KWin here; the tap was invoked from the QML itself, which is the same
  path the click takes).
- qmllint clean.

## What was NOT changed, and why

- **The cloud side already meets the ask**: six providers (Mo Agent, OpenAI,
  Claude, Gemini, OpenRouter, and any OpenAI-compatible endpoint), each with a
  cheap default model, keys in Secret Service and never on disk. It did not need
  a second implementation. Left alone.
- **The picker's list is not clipped.** It looked cut in a screenshot; reading the
  code first showed a `Flickable` with a `ScrollBar` already there — the bar had
  simply faded. Nothing was "fixed".

## Open, needs the owner's call

- **RamaLama is deprecating the ollama:// transport.** Every pull now prints:
  *"Ollama models are no longer compatible with llama.cpp. Support for Ollama
  models will be removed in a future release. Use the Hugging Face <org>/<model>
  shorthand … or specify a transport explicitly."* MoOS's default brain, its whole
  catalog and this new pull path all name `ollama://`. It works today (measured),
  and the HF path works too — `hf://Qwen/Qwen3-8B-GGUF` served and answered
  Arabic beautifully. When RamaLama drops it, every MoOS machine's brain stops
  resolving. Migrating the catalog + `DEFAULT_LOCAL_MODEL` to HF names is a
  one-way change to what installed machines already carry, so it is the owner's
  decision, not an agent's.
- **The login screen is only half MoOS.** Its wallpaper is the branded scene
  (mark, comet ring, "أهلاً بعودتك"), but the moment you touch it the auth card is
  stock Plasma: a generic avatar, and full-colour Sleep/Restart/Shut Down discs —
  the exact class of off-brand icon that was fixed on the LOGOUT screen in session
  F. It cannot be re-skinned from the filesystem: the greeter QML is compiled into
  plasma-login-manager (`qrc:/qt/qml/org/kde/plasma/login/Main.qml`), which exposes
  only `WallpaperPluginId` and `ShowClock`. Screenshots are on the owner's Desktop
  under `MoOS-Screenshots/01-login-logout-2026-07-17/`. Options, both real:
  (a) accept it; (b) ship MoOS's own greeter — the branded icons exist already,
  and this is the last stock surface left in the product.
