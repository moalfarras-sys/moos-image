# MoOS fixes — 2026-07-15 · installer, boot, and the German-language leak

Diagnosed on real hardware (Gigabyte B660, install target = a SanDisk 512 GB SSD)
while running the live image. Symptoms reported: "MoOS won't install on the real
PC", "the installer reaches disk-wipe/system-install then does nothing", "the
language shows German while typing English", "feels like two systems on top of each
other".

Root causes turned out to be a **successful install that could not boot** plus a
**field-shift bug that corrupted the locale**, compounded by a **German keyboard/
language default** that contradicted the installer. All fixed at the source below.
After a new image builds from this commit, an installed system fixes the rest with
`bootc upgrade`.

---

## 1. Installed disk had no UEFI boot entry → "it won't install"  *(the real blocker)*

`moos-install-to-disk` runs `bootc install to-disk --generic-image`, which
**deliberately does not create a UEFI NVRAM boot entry** (a generic image is meant
to be portable/re-imaged). Nothing else created one. On real firmware that means the
machine has no "MoOS" entry, so the moment the live USB is pulled it boots the
previous OS — the install looks like it did nothing. (Confirmed live: the only
non-Windows UEFI entry pointed at the Ventoy USB's ESP, never the target disk.)

**Fix** (`system_files/usr/bin/moos-install-to-disk`, `register_uefi_boot`): after a
successful install, create a `MoOS` efibootmgr entry pointing at the target ESP's
`\EFI\fedora\shimx64.efi` (Secure-Boot friendly; falls back to `\EFI\BOOT\BOOTX64.EFI`),
first in BootOrder. Existing Windows/other entries are left untouched. Best-effort:
never fails the install, but logs loudly.

## 2. Locale/keyboard corrupted by a tab-field shift → "shows German, types English"

The helper parsed the installer's answers with `IFS=$'\t' read`. Tab is an
IFS-**whitespace** character, so `read` **collapses a run of tabs into one delimiter
and drops any empty field**, shifting every later field left by one. With the default
passwordless flow (empty `password`) or an empty `autologin`, the installed system
got `XKBLAYOUT=<locale>`, `LOCALE=<timezone>` → **`LANG=UTC`** (invalid). glibc then
fell back to whatever catalogs were on disk (German was shipped — see #4) and the
keyboard config was garbage. Reproduced exactly: `AUTOLOGIN=us`, `XKBLAYOUT=en_US.UTF-8`,
`LOCALE=UTC`, `TIMEZONE=` in the planted `/etc/moos-setup.conf`.

**Fix**:
- `moos-install-to-disk`: parse the recipe **NUL-delimited** (`mapfile -d ''`), which
  preserves empty fields exactly. No more shift.
- `moos-firstboot`: **validate every value** (defence in depth, also covers the
  Anaconda path) — `AUTOLOGIN`∈{0,1}, `LOCALE` must look like a locale else
  `en_US.UTF-8`, `XKBLAYOUT` must be layout codes (never a locale) else `us`,
  `KEYMAP` sane else `us`, `TIMEZONE` must resolve in zoneinfo else `UTC`. A bad conf
  can no longer break language or keyboard.

## 3. `install.status` never truncated → UI showed a stale failure

The helper appends `PHASE/PROGRESS/DONE/FAIL` lines to the status file the QML polls
but never truncated it, so a previous attempt's `FAIL generic` lingered above a later
`DONE` and the front-end reported failure on a successful retry.

**Fix** (`moos-install-to-disk`): truncate `$STATUS` at the start of every run.

## 4. German was the default keyboard AND a shipped language → "two systems"

The rebrand shipped German as a first-class default, contradicting the installer
(which only ever offers/plants Arabic + English). This is the concrete source of the
"German" complaint and the "two systems on top of each other" feeling:

- `system_files/etc/xdg/kxkbrc`: default layouts were `de,ara` (German + Arabic, **no
  US/English at all**) → **`us,ara`**.
- `system_files/usr/bin/moos-selfcheck`: health check *enforced* `de,ara` → `us,ara`.
- `system_files/usr/bin/moos-lang`: had a reachable `de` branch that flipped the whole
  Plasma UI to German → removed (Arabic + English only).
- `system_files/usr/bin/moos-open`: dropped the `lang/de` route.
- `build_files/build.sh`: stopped installing `langpacks-de` (the German Plasma/GTK
  catalogs an invalid `LANG` could fall back into).

Login screen (plasmalogin), logout screen, `os-release`, `/etc/issue`, plymouth and
the `.desktop` names were audited and were already correctly MoOS-branded.

## 5. Robust disk-free + install retry (the "device is mounted" first-attempt failure)

The first install attempt died with `error: Device /dev/sdX is mounted` because the
live KDE/udisks session re-mounts a previous install's partitions faster than the
single best-effort `umount` pass.

**Fix** (`moos-install-to-disk`): `free_target()` sweeps every child partition **and**
its `/run/media` mountpoints, `swapoff`s anything backed by the disk, and **polls
until the kernel shows the disk free**, retrying the sweep. The install itself runs in
a **bounded retry** that re-frees and retries only on the mount/busy race, never on a
real error.

## 6. Welcome ↔ installer integration

`moos-welcome` now detects a live session (`rd.live.image` / `/run/initramfs/live`)
and passes `--live=1` to the QML. The Welcome hero shows an **"Install MoOS on this
computer"** call-to-action (live only) that opens the installer via a new
`moos://installer/open` route (`moos-open` → `moos-installer`). On an installed system
the button is hidden.

### Applied directly to the already-installed SanDisk (persistent, not in this image)
Because the disk already held a completed-but-unbootable install, two persistent
repairs were made outside the image so it boots correctly now:
- Created the `MoOS` UEFI entry for the target ESP and set it first in BootOrder.
- Corrected the planted `/etc/moos-setup.conf` (`LOCALE=en_US.UTF-8`, `XKBLAYOUT=us,ara`,
  `KEYMAP=us`, `AUTOLOGIN=0`, `TIMEZONE=UTC`) and the deployed `/etc/xdg/kxkbrc`
  (`us,ara`) so the first boot is correct before `bootc upgrade`.
