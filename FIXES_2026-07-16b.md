# MoOS fixes — 2026-07-16 (session B) · the NVIDIA driver install, and three checks that lied

Driven by the owner's report: **"I can't install the driver from Mo AI."** The machine is an
RTX 2080 SUPER running the generic `moos` image on **nouveau**, with the local brain doing
CPU-only inference (~55 ms/token) because the GPU is unusable.

Diagnosed on the running machine, fixed at the source (parity). Every fix below is in the
repo; the device gets them on the next `bootc upgrade`.

See the enduring principles in agent memory: one-system, source↔device parity, ISO hold,
Mo PC Remote is Tailscale-only.

---

## The headline: Mo AI's driver install silently dropped signature verification

Everything about the install path was sound — the button exists (Device panel → "أصلحها الآن |
Fix it"), the route exists (`moos://do/install-nvidia` → `moos-open` → `moai-do`), the action
runs, pkexec is passwordless for `/usr/bin/bootc`, and `moos-nvidia:latest` is current
(same version as `moos:latest`, built the same minute) and correctly signed.

The bug was in what the switch *left behind*. **The journal has it** (2026-07-16 08:05:11):

```
pkexec[19034]: moos: Executing command [COMMAND=/usr/sbin/bootc switch ghcr.io/…/moos-nvidia:latest]
bootc[19034]: Switching from image ghcr.io/…/moos:latest to ghcr.io/…/moos-nvidia:latest
bootc[19034]: Fetching  ostree-unverified-registry:ghcr.io/…/moos-nvidia:latest
bootc[19034]: Staging image for deployment: ostree-unverified-registry:…    ← the bug
```

`bootc upgrade` keeps the origin it was given. **`bootc switch` REPLACES it**, and without
`--enforce-container-sigpolicy` it writes `ostree-unverified-registry:`. An installed MoOS boots
`ostree-image-signed:docker://` — so the one action that moves a user between editions took a
signature-enforcing machine and made it verify nothing. The origin persists, so **every later
`bootc upgrade` would have stayed unverified for the life of the install.**

The owner caught it and backed out by hand at 09:13 and 09:17 —
`bootc switch --enforce-container-sigpolicy ghcr.io/…/moos:latest` — which is why the driver
never got installed and the card is still on nouveau. The complaint was exactly right.

**Fixed** — `system_files/usr/bin/moai-do`:

- `do_install_nvidia` now runs `bootc switch --enforce-container-sigpolicy …`, so switching
  editions lands on the same signed footing a fresh install gets.
- `do_check_drivers` no longer prints a raw `sudo bootc switch …` for the user to type — that
  hand-typed line is the exact path that staged an unverified origin. It points at
  `moai-do install-nvidia`, which carries the confirmation, the Polkit prompt and the flag.

**Gated** — `tests/verify_user_experience.py`: every `bootc switch` in `system_files/usr/bin/`
must carry `--enforce-container-sigpolicy`. Comments are stripped first (`code()`), because the
fix documents the flag right above the call and a gate reading raw text would pass on the prose
after the flag itself was deleted. Proven to bite: removing the flag turns it red.

### Why no gate caught this

`verify_image_experience.py` asserts the **kickstart** deploys `ostree-image-signed:` — and it
still did. Nothing checked the switch the **running system** performs. The install-time end of
the contract was green while the runtime end quietly broke it. Same shape as the traps in
AGENTS.md: *the gate was green while the thing was broken.*

## Three checks that reported a machine that did not exist

### 1. The keyboard check called a correct machine broken

`moos-selfcheck` asserted a literal `us,ara` and kept asserting it after the image default
deliberately became `de,ara` (commit 2bf6a0a — the owner's keyboard is German). So it reported

> ✗ layouts are 'de,ara', expected us,ara — you cannot type English+Arabic
> ✗   cause: ~/.config/kxkbrc overrides the image (delete it, then log out and back in)

…on a machine whose `~/.config/kxkbrc` matched `/etc/xdg/kxkbrc` **exactly**, and told the owner
to delete it. A check that must be edited in lockstep with the thing it checks will eventually
lie. **Fixed** — it now reads the expectation from `/etc/xdg/kxkbrc` (the image's own default)
and compares the live session against that, so it cannot drift again. Verified: `✓ layouts:
de,ara (live, from KWin)`.

### 2. Mo AI promised three Run buttons it never made

The systemPrompt tells the model: *"put the EXACT command in a fenced code block and the app
turns it into a one-click Run button"* — then offers `moai-do setup-gaming`, `setup-windows`
and `install-opencode`. `extractRuns()`'s regex matched none of them. All three are implemented
in `moai-do` **and** routed in `moos-open`; only the regex was short. The model names them
exactly as instructed, the code block renders, and no button ever appears.

The route gates could not see it: they check `moos://` URLs against `moos-open`'s cases, and a
promise that never becomes a URL has no route to check. Same dead promise as the eleven dead
buttons in AGENTS.md, one layer up.

**Fixed** — the three ids added to the regex. **Gated** — `verify_user_experience.py` now
compares the prompt's action list against the regex in both directions, and requires every
button id to be a real `moai-do` action with a `moos-open` route. Proven to bite.

### 3. `grub-boot-success.service` failed on every single login

```
grub2-set-bootflag[2830]: Creating tmpfile failed: Read-only file system
```

The timer fires 2 minutes into every session and writes `/boot/grub2/grubenv` — and on
bootc/OSTree **`/boot` is mounted read-only** (confirmed: `findmnt /boot` → `ro`). Nothing here
consumes the flag: `boot_success` exists for greenboot's rollback counting and **greenboot is
not installed** (MoOS rolls back through bootc/rpm-ostree, which does not read grubenv). So it
was a guaranteed red `systemctl --user --failed` on every boot of every install — including a
fresh ISO — reporting a failure that means nothing.

**Fixed** — `build_files/build.sh` masks the timer and the service (`systemctl --global mask`,
verified against a throwaway `--root` to produce the `/dev/null` symlinks). Masking changes no
behaviour: the flag was already never written.

## Diagnosed, NOT fixed — `drkonqi-coredump-pickup.service` fails 30 min into EVERY session

Found while auditing failed units (`moos-selfcheck` had not seen it yet — it runs before the
30-minute mark, so a check run early in a session reports a clean machine that goes red later):

```
Started drkonqi-coredump-pickup.service - Consume pending crashes using DrKonqi.
drkonqi-coredump-pickup.service: Service reached runtime time limit. Stopping.
drkonqi-coredump-pickup.service: Failed with result 'timeout'.
```

The unit is **stock upstream KDE** (`plasma-drkonqi-6.7.2`) —
`drkonqi-coredump-processor --settle-first --pickup` with `RuntimeMaxSec=30 minutes`.

**It cannot succeed, by construction.** Traced on the running machine with gdb:

- `--settle-first` is a plain `nanosleep`. The constant in `.rodata` is a `timespec` of
  `tv_sec=0x3c` — **60 seconds**, not the 30-minute limit. (A first attempt to observe this
  with a 25-second timeout saw "nothing happening" and nearly drew the wrong conclusion — it
  had not left the settle sleep yet.)
- After the sleep, `main()` calls **`QCoreApplication::exec()`** and never returns:
  ```
  #7  QCoreApplication::exec ()
  #8  main ()
  ```
  Reproduced with **zero** coredumps in scope (`--boot-id` of a crash-free boot): it still sits
  in the event loop forever. With crashes present the stack gains
  `#9 GlobalNotifierTruck::handle(Coredump const&)` above `exec()` — a notification loop — but
  the hang does not depend on that. It hangs either way.

So the service is an **event loop that upstream modelled as a time-limited job**. It runs, does
its work, and is SIGTERMed at `RuntimeMaxSec`; systemd records that as result `timeout`, which
is a **failure**. There is no exit path that ends in success. Every session, on every install.

Not MoOS's doing: MoOS's only coredump change is `coredump.conf.d` (a `MaxUse=1G` cap, which has
nothing to do with whether the processor returns), and the unit itself is untouched upstream.

**Still not fixed, and the deep dive narrowed it to a real choice rather than a puzzle.**
`SuccessExitStatus=` cannot help: it matches exit codes and signals, not systemd's `timeout`
result. That leaves exactly two moves, and both are owner-level calls:

1. **Mask it.** Removes the red for good. Cost: crashes that happened *before* login are no
   longer picked up. Live crashes are unaffected — they arrive through
   `drkonqi-coredump-launcher.socket`, a different, working unit.
2. **`RuntimeMaxSec=infinity`.** Keeps the pickup and removes the red (a unit stopped normally
   at logout is not a failure). Cost: the processor then lives for the whole session alongside
   the socket launcher, which risks *double* crash dialogs — worse than the noise it fixes.

Recommendation: **(1) mask**, if MoOS wants DrKonqi at all. Whether a premium, MoOS-branded
desktop should show KDE's crash reporter is a product decision, so it is left to the owner.

### Side note — a local `just build` leaves 26 coredumps on the host

Building the image on this machine crashed `qwebengine_convert_dict` **26 times** (SIGTRAP,
~253 KB each) — the empty-spell-check-dictionaries issue AGENTS.md already documents as
"crashes inside the build container". The dumps land on the **host**, because podman shares the
host kernel's `core_pattern` (`|/usr/lib/systemd/systemd-coredump`). Harmless (the
`MaxUse=1G` cap exists for exactly this) and invisible to users who never build — but it is why
`coredumpctl` on a maintainer's machine fills with crashes nobody caused at runtime.

## Diagnosed, NOT fixed — `fwupd-refresh.service`

It failed **every run** that actually had to download (06:29, 07:55, 08:35, 09:45 — each exited
1 within the same second, right after `Updating lvfs`). Runs with a warm cache pass: fresh
metadata exits 2, and the unit's `SuccessExitStatus=2 101` turns that green. So the failure
hides whenever the cache is warm and returns when it goes stale (~daily). It is green right now
only because this session refreshed the metadata by hand.

Ruled out by testing, not by guessing:

- **Not the network** — the same refresh as the desktop user downloads fine, repeatedly.
- **Not SELinux** — no AVC denials anywhere near the failures.
- **Not MoOS** — `build.sh` only installs fwupd, and `/etc/fwupd/remotes.d/lvfs.conf` is stock.
- **Not the sandbox's HOME handling** — reproduced `ProtectHome`'s effect (`HOME` unreadable,
  and `HOME`/`XDG_CACHE_HOME` unset entirely) and the refresh still succeeds.
- **Not a stale-cache mixup** — a warm cache exits 2 ("Metadata is up to date"), which the
  unit's `SuccessExitStatus=2 101` correctly counts as success. That is the *green* case.

**Leading suspect, NOT proven — polkit.** `fwupdmgr refresh` downloads the metadata and then
hands it to the running daemon, and that call is polkit-gated by
`org.freedesktop.fwupd.refresh-remote`, whose defaults are:

```
allow_any      = auth_admin      ← a caller with NO session lands here
allow_inactive = yes
allow_active   = yes
```

`fwupd-refresh.service` is `DynamicUser=yes` with no session, so it should fall to `allow_any` →
`auth_admin` → denied instantly, with no agent to authenticate against — which matches the
symptom exactly (exit 1 in the same second, right after `Updating lvfs`, download done, daemon
call refused). Nothing in `/usr/share/polkit-1/rules.d/` grants `refresh-remote`; the shipped
fwupd rule covers only `update-internal`.

**This was NOT confirmed, and the obvious confirmation failed.** Running the refresh from a
`systemd-run --user` transient unit — intended as a session-less stand-in — *succeeded*, because
those units **inherit the login session** (`XDG_SESSION_ID=1`, and `pkcheck` returns authorized).
So the test proved nothing, and creating a genuinely session-less context needs root. The theory
stands on the policy file and the timing, not on a reproduction. **Do not write it up as the
cause until the error message says so.**

That message is the missing piece: upstream's unit sets **`StandardError=null`**, so the one
line explaining the failure is thrown away before journald sees it. Hence the drop-in below —
after the next `bootc upgrade`, the next stale-metadata refresh will name its own cause, and
this either becomes a one-line polkit rule or turns out to be something else entirely.

**Shipped: a diagnostic, not a fix** —
`system_files/usr/lib/systemd/system/fwupd-refresh.service.d/10-moos-log-the-error.conf` sets
`StandardError=journal`. It changes no behaviour and fixes nothing; it exists so the next
failure is readable (`journalctl -u fwupd-refresh.service -b`) instead of silent. **This is
still an open bug.**

## Verified working (no change needed)

- **Parity**: every file in `system_files/` compared byte-for-byte against the running system —
  **620 identical, 0 missing**. The only differences were this session's own edits (pending
  rebuild) and `liveinst.desktop` (below).
- **The local brain is healthy**: `moai.service` (RamaLama/llama-server, qwen3:4b) serving on
  8081, `moai-gateway` on 8080, `moai-control` on 8079, all answering; a real chat completion
  round-trips. It is **CPU-only at ~55 ms/token** — that is the missing NVIDIA driver, not a
  Mo AI bug, and it is what the headline fix unblocks.
- **The chat names the right action.** Asked in Arabic *"عندي كرت شاشة NVIDIA وما في تعريف"*
  with the live machine context injected (`buildContext()` feeds it the device plan), the local
  4B model correctly answers `moai-do install-nvidia`. Without that context it guesses wrong
  (`update-firmware`) — worth knowing, but the app always injects it, so the chat path is fine.
- **`moos-selfcheck`: 37 passed** after the keyboard fix, with the two unit failures above.

## Known dead code (reported, deliberately NOT touched)

`system_files/usr/share/applications/liveinst.desktop` never reaches the image. `COPY
system_files/ /` runs first, then `build.sh` installs `anaconda-live`, whose RPM overwrites that
path, and `build.sh` seds the RPM's copy into shape. The running system proves it: it carries
`X-Desktop-File-Install-Version=0.28` (an upstream artifact absent from the repo file) and
`NoDisplay=true`, where the repo file says `NoDisplay=false`.

The **outcome is correct** — `Name=Install MoOS`, `Icon=moos-logo`, `Exec=moos-installer` — so
there is no user-visible bug, only a file that misleads the next maintainer. Left alone on
purpose: AGENTS.md says an agent that does not fully understand a change to the installer or
branding must stop, and deleting it would need a build to prove the sed still lands. Worth a
deliberate cleanup by someone who can watch a build.
