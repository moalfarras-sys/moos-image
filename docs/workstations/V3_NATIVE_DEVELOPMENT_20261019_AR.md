هذه إعدادات حساب التطوير على جهاز V3 ‏x86_64، فوق النسخة الموقعة1072.
تثبيت هذه البرامج لا يعني أن صورة النظام تحتوي SDK أو أن حسابات مزودي
الذكاء الاصطناعي مسجلة. نسخة النظام الجديدة لها مسار توقيع وإقلاع مستقل.
[إيصال القياسات](../releases/2026-10-19-v3-native-developer-profile.json).

## SDK ونتائج التنفيذ

الحاوية المحلية `moos-dev` تحتوي مترجمات ومكتبات C/C++ وQt6 وGTK وRust
وGo وJDK25 و.NET10 وPython وNode. لا توجد حزم RPM مضافة إلى أصل النظام
الثابت. أوامر الحساب تستدعي Toolbox. كشف فحص الملفات أن الأغلفة الأولى كانت تستدعيه
حتى من داخله؛ حُفظت وأضيف فرع مباشر لأدوات SDK داخل الحاوية. نجحت سبعة
فحوص فعلية من المضيف والحاوية، بينها بناء C++ وتشغيله. أضيف v4l-utils1.32.0
داخل SDK مع أمر محلي للتحكم بالكاميرا، دون إضافة RPM إلى المضيف.

| المسار | النتيجة المنفذة |
| --- | --- |
| C++23 | بناء GCC ثم تشغيل ELF على المضيف؛ CMake/Ninja بنيا المثال كذلك |
| Rust / Go | بناء ثم تشغيل الملفين على المضيف، مع تحقق نتيجة الحساب |
| Java | بناء يستهدف Java21 وتشغيله داخل JDK25 |
| .NET10 | إنشاء Console وبناؤه وتشغيله |
| Python / Node | تنفيذ فحوص المكتبات وحساب النتيجة المتوقعة |
| Flutter3.47.4 / Dart3.13.3 | أرشيف مطابق SHA256 وGit؛ تحليل، اختبار widget عربي وبناء Linux Release |
| Qt6.11.2 QML | تهيئة LSP حقيقية، ملف صحيح بلا تشخيص، وخاصية خاطئة تُكتشف، ثم خروج0 |

خادم QML الأصلي في حساب المستخدم يرفض اختلاف إصدار حزمة Qt عن إصدار SDK.
الاختبار الحالي أكمل دورة LSP في0.439 ثانية. وجود خادم أو إضافة وحده
لا يثبت التحليل. ملف Flutter الناتج ELF وروابط مكتبات المضيف مكتملة؛
لا تُحسب تجربة widget قبولًا للمس أو العرض على الجهاز.

أضيفت إضافات اللغات وQt وClaude Code وOpenCode V2 وGoogle Antigravity
وDev Containers إلى VS Code. الطرفية الافتراضية اسمها MoOS SDK، مع طرفية
MoOS Host مستقلة. إعداد Podman ومسار Flutter وQML محفوظة. ملف إرفاق
`moos-dev` يختار المستخدم `moos` بدل مستخدم الحاوية الافتراضي root؛
اتصل المحرر بالحاوية فعلًا، وبنى C++ من أمر CMake داخل الواجهة في2.549ث
بخروج0، ثم اشتغل الناتج على المضيف. بدأ خادم QML الخاص بـSDK داخل
الإضافة وظهر تحذير الخاصية الخاطئة في المحرر؛ حمّلت إضافة C# المشروع.
هذا قبول لهذه الرحلات المحددة؛ بقية الإضافات مثبتة وليست جميعها مجرّبة تفاعليًا.
الثقة تكون للمشروع المحدد؛ لم تُعطّل حماية الثقة عالميًا.
فحص Code الفعلي يرى Radeon780M وMesa26.2.3 مع compositing/OpenGL/
WebGL/WebGPU مفعلة؛ ترميز الفيديو فيه برمجي. لم يُجر benchmark سرعة.

خادم Go `gopls0.24.0` ومصحح `Delve1.27.2` أضيفا من الوحدات الرسمية
مع تحقق Go checksum database، وضُبطت مساراتهما في Code وملف إرفاق الحاوية.
SDK الأساسي يستخدم Go1.26.9؛ بناء gopls يحتاج Go1.27، فرفضه الإعداد
`GOTOOLCHAIN=local` أولًا، ثم نجح تنزيل أداة Go1.27.2 الرسمية لهذا
التثبيت وحده؛ لم يتغير الإعداد العام. يشخّص gopls ملفًا غير صحيح مع
خروج0؛ قبول الاختبار يعتمد على نص التشخيص الفعلي. Delve توقف عند سطر
محدد وقرأ المتغير42، ثم خرج البرنامج0؛ لم تُرخّص ptrace على مستوى المضيف.

SDK الذكاء الاصطناعي له Python venv وNode project مستقلان تحت
`~/.local/share/moos-dev-platform/`. حُفظ قفل التبعيات. استيراد حزم
Google Antigravity وClaude Agent وAnthropic وOpenAI وMCP وGoogle GenAI
ينجح، وكذلك إنشاء خيارات عميل محلية دون طلب نموذج.
فشل OpenCode SDK فعليًا على Node22 بسبب صياغة `await using`؛ الإصدار
الرسمي Node26.12.0 في حساب المستخدم، بعد تحقق SHA256، يجتاز استيراد
SDKs الأربعة. لم يتغير Node الموجود في `/usr`.

## MCP والتكامل

الخوادم المشتركة هي Sequential Thinking1.0.0 وPlaywright MCP0.0.83
وContext7 عبر HTTP. استُخدمت ملفات ضبط كل عميل بصيغته الحالية، بما فيها
`serverUrl` لـAntigravity وواجهة V2 لـOpenCode. لا مفاتيح حسابات داخل Git.
[صيغة Antigravity الحالية](https://antigravity.google/docs/mcp/).

اختبار MCP الفعلي يهيئ الخوادم، يكتشف1/25/2 أداة، ويشغل Chromium
بـsandbox وملف تعريف مؤقت لقراءة زر عربي من خادم اختبار محلي. يغلق
المتصفح والخوادم بعد الاختبار. Hermes وClaude Code يتصلان بالخوادم
الثلاثة. قراءة Antigravity CLI للقائمة تثبت الضبط فقط؛ لا تثبت اتصالًا
أو محادثة ناجحة قبل تسجيل الحساب.

تنزيل Chromium وحده لم يكفِ: الطلب الأول بحث عن Chrome غير موجود.
حُفظ الفشل ثم ضُبط مسار Chromium الفعلي. نواتج المتصفح أصبحت داخل
cache خاص بالمستخدم، بعد نقل أول ملف اختبار مولّد خارج المستودع.

OpenCode CLI نفذ طلبًا اصطناعيًا بالنموذج المجاني الصريح
`opencode/glm-5.3-flash-free`: اكتملت أداة القراءة وأعاد النص الصحيح
لملف لم يُعطَ محتواه في الطلب. نجح المسار المطلق؛ طلبا المسار النسبي
قبله رفضا الملف غير الموجود وحُفظا. هذا قبول محدود لأداة ونموذج،
ولا يثبت حسابات المزودين الأخرى أو سير عمل مشروع كامل.

## حدود القبول الحالية

البرامج المحلية تفتح وتبقى بعد انتهاء أمر الإطلاق. روجعت نوافذ Code
وOpenCode وClaude، وظهر طلب Google في Antigravity App. لا تعني هذه
النوافذ أن كل ميزات الحسابات أو المحادثات أو الخلفية تعمل بعد الإقلاع.

KWallet معطّل افتراضيًا في MoOS. محاولة فتح إعداد المحفظة انتهت بمهلة،
ثم أجّل المالك إنشاءها وتسجيل الحسابات. لم تُنشأ محفظة جديدة؛ أُعيد
إعداد الحساب الأصلي وقُرئ `isEnabled=false` فعليًا. أوقفت خدمتا الإعداد
اللتان بدأتهما المحاولة بعد تحقق غياب ملفات المحافظ؛ فحص MoOS اللاحق
ينجح54/54. إن عاد تطبيق إلى طلب المحفظة، يبقى تفعيلها المشفر خطوة للمالك. النسخة السابقة
محفوظة خصوصيًا، ولا تغيير في PAM أو masks النظام. عند العودة للدخول
يلزم إنشاء محفظة مشفرة أولًا؛ لا يُختار تخزين الأسرار كنص عادي لتجاوز الطلب.

سُجلت في Antigravity IDE2.5.5 أعطال SIGTRAP وSIGSEGV حتى بملف تعريف
نظيف دون إضافات المستخدم. العنوان يقع في `DirTreeDeleter` من
`@parcel/watcher2.5.1`، والتفريغ ناقص. التحكم الأول بإنشاء/نقل/حذف
وإلغاء الاشتراك نجح؛ لكنه لم يختبر الإغلاق مع اشتراكات حية. ذلك التحكم
الأخير أعاد SIGABRT وdouble-free في المكتبة القديمة؛ النسخة الرسمية2.6.0
نجحت ثلاث مرات بنفس Node26 والملف الاصطناعي. يتوافق هذا مع
[إصلاح ترتيب تدمير المتغيرات لدى المصدر](https://github.com/parcel-bundler/watcher/pull/216).

استُخدمت نسخة reflink معزولة من التطبيق، وHOME وruntime وناقل D-Bus
وخادم Wayland مستقلون. تحققت بيئة daemon نفسه. اجتازت ثلاث دورات
فتح وإغلاق طبيعي وإعادة فتح، ورصد مراقب الملفات60 حدثًا خامًا متوقعًا،
وخرج المراقب0 كل مرة مع قراءة تحميل المكتبة الجديدة من `/proc`.
فشل الاختبار الخاص الأول بسبب طول مسار Unix socket؛ حُفظ عطل teardown
الخاص به وصُحح المسار. لا يُنسب ذلك إلى compositor جلسة المالك.

بعد ذلك حُفظت مكتبة الناشر القديمة في أرشيف خاص وقُرئت من داخله للتحقق،
وطُبق تحديث المكتبة2.6.0 وملفها الأصلي Linux x64 في نسخة حساب المستخدم
فقط. أكدت دورة أصلية إضافية تحميل الملف الجديد والخروج الطبيعي0 للتطبيق
ومراقبه. لم تُعطّل الحماية أو GPU، ولم تُعدّل صورة النظام. قد يستبدل تحديث
الناشر هذا التصحيح؛ يلزم قراءة الإصدار مجددًا بعده. لا تثبت هذه الضوابط
حل جميع أعطال renderer/zygote التاريخية أو اكتمال تجربة المحرر والحساب.
واجهة الدخول الأصلية ما زالت تطلب Google؛ تسجيلها مؤجل حسب طلب المالك.
[إثبات التصحيح وتجهيز1078](../releases/2026-10-19-v3-native-staged1078-watcher-proof.json).

حُفظ كذلك انهيار conmon في تنظيف جلسة تنفيذ SDK، بعد إكمال الأوامر
الناجحة؛ لا يُحسب فشلًا لبناء البرامج ولا دليلًا على سلامة runtime الكامل.
فشلا تثبيت Java21 وإطلاق أرشيف Code الأول محفوظان، ثم نجحت المثبتات
المصححة؛ أزيلت حالتا failed لوحدتي الاختبار المحددتين بعد حفظ سجلاتهما.
لم تُمسح تقارير الأعطال. الفحص اللاحق يرى صفر وحدات نظام/مستخدم فاشلة،
واتصال Remote نشطًا دون إعادة تشغيل، ولا تحذيرات kernel جديدة في فترة الفحص.

الوصول للملفات والأجهزة يتم بصلاحيات حساب المالك. إدارة النظام تستخدم
التفويض المعتاد؛ لا تشغيل دائم كـroot ولا تغيير sudoers. الاتصال البعيد
والشاشات والصوت لم تُعد تشغيلها. إعادة التشغيل، اختبار الصورة الجديدة
والبصمة الباردة، وحد شحن BIOS تبقى أعمال قبول منفصلة مع حضور المالك.

فشل أول مثبت SDK لأن Java21 غير متاح في القناة، ثم اكتمل بـJDK25.
أول فحص Flutter استعمل `rg` غير الموجود في بيئة وحدة systemd داخل شرط
فلم يكفِ خروجه0؛ حُفظ هذا القصور ثم أعيدت الأوامر بأكواد خروج مستقلة
وفُحصت روابط ELF ببايثون. جميع النتائج النهائية موجودة في الإيصال.

بوابات المستودع المحلية اكتملت بخروج0: 2687 حالة unittest ضمن198
ملخصًا، إضافة إلى بوابات السكربتات. جرى إعداد التوثيق أثناء ذلك الفحص؛
فحوص خصوصية وروابط التوثيق النهائية تُنفذ منفصلة على الملفات المحفوظة،
ولا يُنسب الفحص الطويل إلى commit لم يكن مكتوبًا عند بدايته.

## REA وGhidra — إعداد 21 أكتوبر على1078

أضيف ملف إعداد اختياري قابل للفحص في
[`scripts/setup-analysis-tools.py`](../../scripts/setup-analysis-tools.py)،
مع [النسخ المقفلة وتعليمات التثبيت](../../scripts/workstation/analysis-tools/README.md).
يعيد استخدام Node26.12.0 وJDK25.0.4.1 في `moos-dev` الموجود. ثبتت REA6.7.0
من حزمة npm الرسمية، وGhidra12.1.4 من أرشيف الناشر الرسمي؛ لا يوجد JDK
أو SDK مكرر ولا RPM إضافي على المضيف. جميع اعتماديات npm مقفلة، وتشغيل
سكربتات الحزم معطل. `gitHead` غير منشور لحزمة REA؛ التحقق يثبت حزمة الناشر
نفسها ولا يدعي مطابقتها مع commit مستقل في GitHub.

نجح التحقق من ملفات الأرشيفين مقابل النسخ المثبتة فعليًا، وحُفظت ملفات
التشغيل السابقة قبل تحديثها. ينجح `--check` دون تغيير المحتوى أو أزمنة الملفات.
نجح تشغيل CLI وخادم MCP من مشغلات الحساب الجديدة، مع207 أدوات معلنة وفحص
هوية الحزمة والفهرس. فتحا ملف ELF تجريبيًا مملوكًا لنا، وحللا `moos_blend`،
ثم أغلقاه؛ تطابق الكود المستخرج وبصمة الملف. هذا قبول لهذه الرحلة، ولا يعني
اختبار الأدوات207 كلها أو تسجيل حسابات المزودين.

خادم REA مسجل محليًا في Codex؛ الجلسة المفتوحة تحتاج إعادة تشغيلها المعتادة
لقراءة التسجيل الجديد. المثبت لا يعيد كتابة إعدادات MCP ولا ينسخ المفاتيح.
Ghidra يملك اختصارًا أصليًا في قائمة Plasma. كشف اختبار الواجهة نافذة
رئيسية فارغة على Wayland؛ ظهر محتواها بإعداد OpenJDK داخل عملية الواجهة
فقط، وأعاد المشغّل القديم العطل عند استرجاعه. المشغّل المثبت المصحح فتح
مشروع ELF تجريبيًا وملفه داخل CodeBrowser، وعرض الكود المستخرج للدالة
